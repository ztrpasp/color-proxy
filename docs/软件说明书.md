# color-proxy 服务端 软件说明书 v1

> 本说明书描述「共生网络 Web 代理终端 —— 服务端（提供端）」v1 最小功能版本的
> 架构、实现、运行与限制。背景与需求见 `docs/PRD-v1.md`，设计见 `docs/design-server-v1.md`，
> 共生网络背景见 `技术文档/共生网络技术要点（终端开发相关）.md`。

---

## 1. 概述

`color-proxy` 让传统 Web 服务也能借助共生网络（CoLoR）的跨域获取能力被访问。
完整系统由四个角色构成：

- **消费端**（浏览器侧正向代理）—— 截取浏览器 HTTP 请求，转为 CoLoR 流量。
- **提供端**（Web 服务侧反向代理）—— **本软件**，发布 URL、回源、回送响应。
- **RM / BR** —— 共生网络基础设施，需求不变，不在本项目改动。

本软件即**提供端**。它把配置中的 URL 发布为 SID，接收消费端经共生网络发来的 HTTP 请求，
向真实后端（origin）回源取响应，再把响应经共生网络发回消费端。

**v1 最小功能**：不实现 ESS 端到端加密、可靠传输（滑动窗口/重传）、并发（同 `(SID,消费端NID)` 串行）、
HTTPS、HTTP 请求分片；**已实现 HMAC**（对发出的 DATA 报文生成/填充，供 BR 校验，见 §4）。

## 2. 系统架构

### 2.1 分层

```
┌─────────────────────────────────────────────────────────┐
│ 业务层  registration / publish / handlers / origin       │  注册·发布·握手·回源
├─────────────────────────────────────────────────────────┤
│ 报文层  protocol(constants/utils/sid/packets/control)    │  CoLoR 编解码
│ 报文构造 messages                                         │  发往消费端的 DATA
├─────────────────────────────────────────────────────────┤
│ 传输层  transport(receiver/sender)                        │  IP 协议号 150 收发
├─────────────────────────────────────────────────────────┤
│ 装配    provider  ·  入口 main  ·  配置 config · 状态 state │
└─────────────────────────────────────────────────────────┘
                         ⇅ scapy + 原始套接字 + Npcap
```

### 2.2 模块职责

| 模块 | 职责 |
|---|---|
| `protocol/constants.py` | IP 协议号、报文类型/首字节、标识长度、`load[0]` 标志（TUNNEL/REQUEST/RESPONSE、LAST） |
| `protocol/utils.py` | 校验和（16 位反码和）、整数↔字节序、IPv4↔小端字节、HMAC（`calc_hmac`：MD5 取末 4 字节） |
| `protocol/sid.py` | SID 生成与表示：`SID = NID ‖ SHA1(去 query/fragment 后的 url)`，72 位十六进制字符串 |
| `protocol/packets.py` | scapy 声明式报文：`ColorGet` / `ColorData`（含两处修正）/ `ColorAnnounce`+单元 |
| `protocol/control.py` | CONTROL 手工编解码：注册请求构造、域内同步回复解析 |
| `transport/receiver.py` | 原始套接字接收（proto 150 + `SIO_RCVALL`），过滤本机包，回调负载 |
| `transport/sender.py` | scapy `sendp` 发送（`Ether/IP(proto=150)/CoLoR`），缓存 MAC/网卡 |
| `messages.py` | 构造发往消费端的 DATA 报文（隧道/响应）；`is_ack` 判别 |
| `config.py` | 读取/校验 `config.json` |
| `state.py` | 运行期状态：注册标志、域内代理/BR 表、Web 服务表、未决事务表（均加锁） |
| `registration.py` | 向 RM 注册、处理 RM 同步回复 |
| `publish.py` | 把配置的服务发布为 SID（发 ANN） |
| `handlers.py` | `handle_get`（回隧道 DATA）/ `handle_ack`（取 HTTP 请求并起回源） |
| `origin.py` | `OriginWorker`：新建 TCP 回源、规整请求、读到 EOF、发响应 DATA |
| `provider.py` | 装配收发与分发，串起注册/发布/处理 |
| `main.py` | 命令行入口 |

## 3. 工作流程（先拉后推）

```
浏览器        消费端C(NID_C)                  RM/BR        本软件 提供端P(NID_P)        真实后端 origin
  │ HTTP请求 ─▶│                                                │                            │
  │            │ ① GET(SID, nid=C, SegID=tx) ─────────────────▶ │ handle_get                 │
  │            │                                                │  校验SID∈已发布            │
  │            │                                                │  定回址→记未决事务         │
  │            │ ◀── ② 隧道DATA(B=0,空载[TUNNEL],带PID序列) ───── │  build_data_packet         │
  │            │ 取PID隧道                                       │                            │
  │            │ ③ ACK(B=1, load=[REQUEST]+HTTP请求) ──────────▶ │ handle_ack                 │
  │            │                                                │  取请求→OriginWorker ───── ▶│ 新建TCP/规整请求
  │            │                                                │                  HTTP响应◀──│ 读到EOF
  │            │ ◀── ④ 响应DATA(B=0, load=[RESPONSE]+分片)×N ──── │  best-effort 发送           │
  │ ◀ 写回TCP  │                                                │                            │
```

对应代码中的四个阶段：
- **state A** `handlers.handle_get`：校验 SID、按 PID 序列判域内/跨域定回址、记 `PendingTx`、发隧道 DATA。
- **state B** `handlers.handle_ack`：校验 `load[0]` 为 HTTP_REQUEST、取出请求、查未决事务、起 `OriginWorker`。
- **state C** `origin.OriginWorker._fetch`：每请求新建 TCP 到 origin，规整请求（绝对 URI→源站形式、强制 `Connection: close`），读到 EOF；失败合成 502。
- **state D** `origin.OriginWorker._send_response`：响应按 1200 B 分片，逐片封 DATA（末片置 LAST）发回，无重传。

## 4. 协议与报文实现要点

- **报文类型**：IP 协议号 150，Version=7；ANN(0x71)/GET(0x72)/DATA(0x73)/CONTROL(0x74)。
- **SID**：`N_sid = 本机 NID(16B)`，`L_sid = SHA1(去 query/fragment 后的 URL)(20B)`，键为 72 位十六进制串。
- **`load[0]` 约定**：高 2 位 WebMsgType（`0x10` TUNNEL / `0x20` HTTP_REQUEST / `0x30` HTTP_RESPONSE），低位 `0x01` LAST。
- **DATA 校验和仅覆盖包头**（`data[0:Header_Length]`）；GET/ANN/CONTROL 覆盖整包。
- **HMAC（已实现）**：对**发出的每个 DATA**（隧道/响应）填充报文头 HMAC 字段（`Flags` 置 `C=0x04`，DATA 的 HMAC 字段 4 字节）。算法为**无密钥 MD5 取末 4 字节**（`protocol/utils.py:calc_hmac`，对照参考实现 `CalcHMAC`），覆盖范围为包头（偏移 10 起）+ 负载 + 末尾 4 字节 `Random_Num` 种子；种子取自 GET 报文的 `Random_Num`（R=1 时），隧道 DATA 与响应 DATA **复用同一种子**（存于 `PendingTx.random_num`）。在**校验和之前**计算，使校验和覆盖最终 HMAC，从而通过 BR 校验。**仅生成/填充，不校验入站**；消费端 GET/ACK 暂不携带 HMAC。实现见 `protocol/packets.py:ColorData.post_build`、`messages.py:build_data_packet`。
- **字节序**：长度/SegID/PID/MTU/控制报文长度/IP(控制) 为小端；校验和为大端；NID/SID 为字节数组。
- **回送路径**：跨域 `R=1`，`PID_List = GET 的 PID 序列 + 保留 PID(0)`，`PID_Pointer = 有效 PID 数`；域内 `R=0`、无 PID。
- **`ColorData` 相对参考实现的两处修正**（见 `packets.py`）：
  1. `Source_NID` 出现条件加入 `B==1`——ACK 报文线上含两个 NID（提供方 + 消费方）。
  2. `post_build` 自动回填 `PID_Pointer = len(PID_List) − R`。
- **CONTROL 手工编解码**：RM 同步表(Subtype=6)的代理条目是「IP 在前、NID 在后」，与注册请求(Subtype=5)相同；新代理通知(Subtype=8)是注册载荷原样转发（20 字节，没有条目数）。因 tag=6 是「条目数 + 两张变长表」且要先截掉以太网填充再校验，仍在 `control.py` 手工解析。（2026-10-28 勘误：此前误写为「NID 在前」并按此实现，同域回址因此失效。）

> ⚠ **scapy 使用注意**：设置 `Flags` 必须在**构造时整体赋整数值**（如 `ColorData(Flags=0x22, ...)`），
> **不可**用 `pkt.Flags.X = True`（scapy 会跨实例共享同一可变标志对象，导致标志位污染）。
> DATA 标志位：`S=0x02`、`C=0x04`（HMAC）、`R=0x20`、`B=0x40`。

## 5. 运行

### 5.1 环境与依赖
- Python 3.8+（开发与验证使用 3.13）。
- `pip install -r requirements.txt`（仅需 `scapy>=2.5.0`）。
- **Windows 需安装 [Npcap](https://npcap.com/)**（scapy 收发链路层报文）。
- 运行需**管理员权限**（原始套接字 + `SIO_RCVALL`）。

### 5.2 配置 `config.json`

```json
{
  "nid": "a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1",
  "ipv4": "10.0.1.6",
  "rm_ipv4": "10.0.0.1",
  "services": [
    {"url": "http://prov.local/hello.html", "origin_host": "127.0.0.1", "origin_port": 8000}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `nid` | 本机节点标识，32 位十六进制（128 bit） |
| `ipv4` | 本机 IPv4（绑定原始套接字、注册给 RM） |
| `rm_ipv4` | 资源管理器 IP |
| `services[].url` | 对外发布的 URL（`L_sid = SHA1(去 query/fragment 后的 URL)`，故同 path、不同 `?query` 命中同一 SID） |
| `services[].origin_host/port` | 该 URL 的真实后端地址，省略则取 URL 自身主机端口 |

### 5.3 启动

```
copy config.example.json config.json   # 按需修改
python -m colorproxy.main config.json   # 以管理员权限运行；-v 输出调试日志
```

启动序列：开启收包 → 向 RM 注册并等待同步（最多重试 3 次）→ 发布服务（ANN）→ 阻塞等待请求。

## 7. 错误处理与日志

- 收包线程对**单个坏包**捕获异常并忽略，不影响整体运行（`provider._on_payload`）。
- GET 的 SID 未发布、无法定回址 → 丢弃并告警（消费端最终超时）。
- ACK 无匹配未决事务、`load[0]` 非 HTTP_REQUEST → 丢弃并告警。
- 回源连接失败/超时 → 合成 **502 Bad Gateway** 作为响应发回，避免浏览器挂起。
- 日志用标准 `logging`，`-v` 开启 DEBUG。

## 8. 已知限制与演进（v2+）

- CoLoR 段 **best-effort**，无重传；大响应或丢包时页面可能不完整 → 可复用参考实现的滑动窗口（`slideWindow.py`）做可靠传输。
- 假设单个 HTTP 请求可装入一个 IP 包；不支持大 body 的请求分片。
- 不实现 ESS 端到端加密。**HMAC 已实现**（对发出的 DATA 生成/填充以通过 BR 校验，见 §4）；不校验入站 HMAC，消费端 GET/ACK 暂不带 HMAC。
- 同 `(SID, 消费端NID)` 并发请求按 last-wins 串行；如需并发可引入事务 ID（建议复用 SegID 字段）。
- 仅服务已发布到共生网络的 URL；仅 HTTP（无 HTTPS）；仅 Windows。
