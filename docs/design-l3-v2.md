## 0. 背景与本轮锁定决策

### 0.1 为什么要 L3 模式

v1 的 HTTP 代理在应用层打断了端到端 TCP：浏览器↔消费端代理是一条 TCP，提供端代理↔源站是另一条 TCP，**中间那段 CoLoR 不被任何 TCP 覆盖**（`PRD-v1.md §8`）。要支持 FTP / 视频流 / 数据库等更多应用，沿这条路只有两个选择：逐协议写适配器，并且在 CoLoR 层自己造可靠传输。

L3 模式把**完整的内层 IP 包**（含 TCP/UDP 头）作为 CoLoR DATA 的载荷透传。于是：

- **端口、序号、重传、流控天然在内层传输层头部里**，CoLoR 不需要端口字段，也不需要滑动窗口。
- 端到端 TCP 连接的两端仍然是真实客户端与真实服务端，**连接不被打断**。
- 一套机制覆盖所有 TCP/UDP 应用，**不需要逐协议适配**。
- CoLoR 退回它该待的位置：一段尽力而为的**命名承载**，等价于隧道场景下的一条链路。这不违背分层，是回到分层。

注意这不会出现 TCP-over-TCP 崩溃：隧道是数据报式的，没有上下层重传叠加。

### 0.2 代价（必须在论述中写明）

服务级粒度（ip+port）意味着：

- **失去网内缓存**：一条 TCP 字节流的分片不可缓存、不可去重、不可多源取回。
- **失去内容级管控**：同一 `ip:80` 下的不同路径不再可区分。

保留的是：命名路由、基于名字的准入控制、提供方移动性、源地址无关的路由。

因此 v2 **不替换** v1，而是形成**双粒度统一标识框架**：

| 模式 | L_sid 来源 | 适用 | 网内缓存 | 端到端 TCP |
|---|---|---|---|---|
| 内容级（v1，保留） | `SHA1(去 query 的 URL)` | HTTP 可缓存资源 | 可 | 断开 |
| 服务级（v2，新增） | `SHA1(proto://ip:port)` | FTP / 视频 / 数据库 / 任意 TCP·UDP | 不可 | 保持 |

同一套 SID/NID/PID 承载两级粒度，细粒度换缓存、粗粒度换通用性。

## 1. 架构总览

### 1.1 双路径结构

每个代理进程内部有**两条互不相交的收发路径**，这是理解整个设计的关键：

```
            路径一：CoLoR 承载（外层包）              路径二：业务数据（内层包）
        ═══════════════════════════════          ═══════════════════════════════

           raw socket(AF_INET,SOCK_RAW,150)            TUN 设备 color0
           + SIO_RCVALL（Windows 收）                  (Wintun / /dev/net/tun)
                      ↕                                          ↕
              物理网卡 eth0                              内核 IP 栈 / 路由表
              (10.10.0.2 或 172.10.0.2)                          ↕
                      ↕                                   本机应用进程
            RM / BR / 对端代理                       (客户端 或 源站服务)
```

- **路径一只承载外层报文**：`IP(proto=150) / CoLoR 头 / load`。它永远走物理网卡，永远不进 tun。
- **路径二只承载内层报文**：完整的 IPv4 包，含 TCP/UDP 头。它永远走 tun，永远不出物理网卡。
- **代理进程是两条路径之间唯一的桥**：从 tun 读到的包封进 CoLoR 发出去，从 CoLoR 收到的包拆出来写进 tun。

> ⚠️ **两条路径的地址空间必须严格隔离。** 一旦某个外层目的地址落进了 tun 路由覆盖的范围，外层包会被自己的路由表吞进 tun，形成死锁。§2.4 给出具体的隔离规则与检查方法。

### 1.4 为什么注入用 `write(tun)`

提供端拆出内层包后，通过 `write(tun_fd)` 交给自己的协议栈。内核把它当作**从 tun 网卡收到的包**，走正常的 `ip_rcv` 输入路径。这是 WireGuard / OpenVPN / Tailscale 的标准做法。

内核拿到包后的判定：

```
write(color0) → 内核在 color0 上执行输入处理 → 查内层 dst
   ├─ dst 是 color0 自己的地址        → 本机投递（强/弱主机模型都放行）
   ├─ dst 是本机其它网卡的地址        → 弱主机放行；强主机丢弃  ← D9 落在这一行
   └─ dst 不是本机地址                → 开了 IP 转发则转发，否则丢弃
```

按 D9，发布的服务地址是物理网卡地址 `172.10.0.2`，包却从 color0 递上来，落在第二行。Windows 默认强主机接收会丢弃，因此必须开弱主机开关（§2.3）。

Windows 上不使用 raw socket 自发自收的替代路径：XP SP2 之后微软封了 raw socket 发送 TCP 与伪造源地址，这条路在 Windows 上是死的。

## 2. 拓扑与地址规划（契约）

### 2.1 地址规划表

```
┌────────────── 消费端机器 C ──────────────┐   ┌────────────── 提供端机器 P ──────────────┐
│ 物理 eth0  10.10.0.2/24                  │   │ 物理 eth0  172.10.0.2/24                 │
│   └ 承载外层 CoLoR (proto=150)           │   │   ├ 承载外层 CoLoR (proto=150)           │
│   └ 本域 RM/BR 在 10.10.0.0/24           │   │   ├ RM 172.10.0.5                        │
│                                          │   │   └ **源站服务监听在这里**               │
│                                          │   │                                          │
│ color0 (Wintun)  10.99.1.1/24  MTU 1280  │   │ color0 (Wintun) 10.99.1.254/24 MTU 1280  │
│   └ 内层包源地址 = 10.99.1.1             │   │   └ 仅作路由落点，不承载服务             │

│ 路由: 172.10.0.2/32 → color0  ★主机路由  │   │ 路由: 10.99.1.0/24 → color0              │
│                                          │   │ 弱主机开关: color0 上两个（§2.3）        │
└──────────────────────────────────────────┘   └──────────────────────────────────────────┘
                     │                                            │
                     └────────── CoLoR (IP proto 150, RM/BR) ─────┘
```

> ⚠️ **rev.4 起实际采用的是 §2.5 的虚服务地址方案（D18）**，上面这张图画的是 D9。
> 两者只差「服务地址取物理还是取 tun 地址」，其余契约完全相同。下表两列并列，
> **部署按 D18 那一列**；需要在论述中强调「发布的是真实物理地址」时切回 D9 列，
> 只改 `l3.services[].ip` 与消费端的 `capture_routes`，并按 §2.3 开四个开关。

| 项 | **D18（采用，§2.5）** | D9（备选，见 §2.3） |
|---|---|---|
| 对外发布的服务地址 | **`172.10.9.2`**（= 提供端 color0 自己的地址） | `172.10.0.2`（提供端物理网卡地址） |
| 提供端 tun `color0` | `172.10.9.2/24`，MTU 1280。**服务就绑在它身上** | `10.99.1.254/24`，MTU 1280，只作回程路由落点 |
| 消费端 tun `color0` | `10.99.1.1/24`，MTU 1280。**内层包源地址就是它** | 同左 |
| 消费端路由 | `172.10.9.2/32 → color0`（**主机路由**，见 §2.4） | `172.10.0.2/32 → color0` |
| 提供端路由 | `10.99.1.0/24 → color0` | 同左 |
| 弱主机模型开关 | color0 自己的两个（§2.3 勘误） | 两张网卡上四个（§2.3） |

D9 下两端 tun 同处 `10.99.1.0/24`，相当于一段跨隧道的共享子网；D18 下提供端 tun 单独
占 `172.10.9.0/24`，消费端 tun 仍在 `10.99.1.0/24`，由提供端的 `peer_routes` 覆盖。
两种情形 TUN 都是 L3 设备，不涉及 ARP，不会有二层冲突。

> **单机跑不了完整一条流**（rev.4 实测结论）：无论 D9 还是 D18，两端装在同一台机器上
> 时**两个内层端点都是本机地址**，客户端 `connect` 被内核直接投给本地协议栈、回程也
> 走环回，TCP 建得成功但一个包都没进隧道。M1c / M4 必须两台机器，见 §11 M1c 行。

### 2.2 内层包的源地址是 tun 地址，不是物理地址

消费端路由把去往 `172.10.0.2` 的流量导向 color0，内核随即从 color0 上选源地址，所以：

```
内层包：src = 10.99.1.1 (消费端 color0)  →  dst = 172.10.0.2 (提供端物理网卡)
```

**这是无法绕开的**：应用不会显式 bind 到 `10.10.0.2`，内核的源地址选择必然落到出接口上。D2 要的"不做 NAT、地址端到端不变"完全成立——内层地址全程不被改写、稳定、唯一；只是"真实源地址"指的是隧道地址空间内的地址，不是机器的物理网卡地址。

**纯路由模式的硬约束**：提供端要靠内层地址定位消费端，因此**每个消费端的 tun 地址必须全局唯一**。原型单消费端无影响，多消费端时按 `10.99.1.1 / 10.99.1.2 / …` 静态分配。rev.3 起这不再只是一句约定：地址写进提供端的 `peers[]`（§9.1），并在每个包上校验（§7.2 注入第 5 步、§7.3）。

### 2.3 弱主机模型开关（D9，仅提供端）

> **rev.3 实测修正（重要）**：rev.2 这一节写的「仅 color0」**是错的，两个开关只打在 color0 上不够**。2026-09-20 的 M1b 实测（`tools/l3_m1b_inject.py`）证明：必须在 **color0 与"服务地址所在的那张网卡"两边都打开**，否则注入的包进不了 TCP 协议栈（连 RST 都不回），症状与防火墙拦截、源站只听回环完全一样。照 rev.2 逐字部署必然踩这个坑。

内层包目的 `172.10.0.2` 绑在物理网卡，却从 color0 递上来；回程源地址 `172.10.0.2` 属于物理网卡，却要从 color0 发出。两个方向都违反 Windows 默认的强主机模型，必须打开四个开关：

```powershell
# 查接口索引/别名
netsh interface ipv4 show interfaces

# 仅提供端。<svc_if> = 服务地址（172.10.0.2）所在的那张网卡
netsh interface ipv4 set interface <color0_idx> weakhostreceive=enabled
netsh interface ipv4 set interface <color0_idx> weakhostsend=enabled
netsh interface ipv4 set interface <svc_if>     weakhostreceive=enabled
netsh interface ipv4 set interface <svc_if>     weakhostsend=enabled
```

**实测依据**（同一台机器、同一次会话内的三组对照）：

| 目标地址 | color0 两开关 | 服务网卡两开关 | 结果 |
|---|---|---|---|
| `10.99.1.254`（color0 自己的地址） | 开 | — | **SYN-ACK** |
| `172.10.0.2`（另一张网卡的地址） | 开 | 关 | 无任何回应，协议栈里也没有半开连接 |
| `172.10.0.2` | 开 | 开 | **SYN-ACK** |

第二行是关键：包确实写进了 tun（同期能从 tun 读到 IPv6/IGMP 等正常噪声，读写通路是活的），但 TCP 协议栈根本没接受它。

> 尚未隔离**最小**开关集合：第三组实验里服务网卡的 `weakhostsend` 与 `weakhostreceive` 是一起打开的，所以只能确定"两边都开可行、只开 color0 不行"，不能确定服务网卡侧是否两个都必需。四个全开是安全的超集，部署按上表执行即可。

**安全影响**：在**物理网卡**上打开 weakhostreceive，意味着该网卡会接受目的为本机其它接口地址的包，攻击面比默认的 strong host 略大。真正约束边界的是 §7.3 的逐包准入校验，不是主机模型。

**这也是 §2.5 方案更省事的实测证据**：服务发布在 color0 自己的地址上时（上表第一行），**服务网卡那两个开关不需要**——D9 要换来的代价，正是在物理网卡上额外放宽主机模型。

> ⚠ **rev.4 勘误（2026-09-21 真机发现）**：这一段原先写的是「四个开关一个都不需要」，
> **与上表第一行自相矛盾**——那一行的「color0 两开关」列是**开**，「服务网卡两开关」
> 列才是「—」。也就是说唯一成功的那次实验里，**color0 自己的两个开关是开着的**，
> 从未被隔离验证过是否可以关掉。照原话部署（四个全关）的症状是：包写进了 tun、
> `tun_tx` 也涨，但协议栈**连 RST 都不回**，与防火墙拦截完全同症状。
>
> 因此结论修正为：**§2.5 省掉的是服务网卡那两个；color0 自己的两个按已知可行的配置
> 保持开启**，待后续单独隔离。实现已跟进：`ProviderL3Service._check_host_model` 在
> §2.5 下仍检查 color0 的两个开关，`tools/l3_m1c_loopback.py` 则直接为它自己创建的
> tun 打开（适配器删除即消失，不留残留）。

**消费端不需要任何开关**：出向包源地址 `10.99.1.1` 本就属于 color0，回程包目的 `10.99.1.1` 也属于 color0，两个方向都是"收发网卡自己的地址"，强主机模型天然满足。

**Linux 侧无需对应操作**：Linux 默认就是弱主机模型。唯一要留意的是 `rp_filter`——内层源 `10.99.1.1` 的反向路由指向 color0（因为有 `10.99.1.0/24 → color0` 的路由），反向路径检查能通过，默认配置即可。所以 D9 不损害后续的 Linux 移植。

### 2.4 路由隔离规则（必须逐条核对）

这是 D9 方案下**最容易出事**的地方。规则：

> **路径一的任何外层目的地址，都不得落进路径二的 tun 路由覆盖范围。**

外层目的地址包括：本域 RM、本域全部 BR、本域全部 Peer 代理。具体措施：

1. **消费端只配 `/32` 主机路由**，不要配 `172.10.0.0/24 → color0`。后者会把提供端域的 RM `172.10.0.5` 一起吞进 tun。原型只有一个提供端，主机路由完全够用；将来多提供端就多配几条 `/32`。
2. **外层发包必须显式指定物理接口**，不依赖路由表。现有 `sender.py` 用 scapy `sendp` 在 L2 指定 iface 发送，天然绕过路由表；将来改成 raw socket `sendto` 时要显式 `bind` 到物理地址并设 `SO_BINDTODEVICE` / 指定源地址，**这一条要写进代码注释**。
3. **部署前必查：本方案要求消费端与提供端不在同一个 CoLoR 域。**

   第 3 条是硬前提，理由：如果同域，消费端的上行 DATA 会直接发往 `PeerProxys[NID_P] = 172.10.0.2`，而这个地址正好被 `/32` 主机路由指向了 color0 —— **外层包被自己的 tun 吞掉，链路彻底死锁**。对称地提供端也一样。

   按 D5 的地址规划（消费端 `10.10.0.0/24` + 自己的 RM，提供端 `172.10.0.0/24` + RM `172.10.0.5`）是跨域部署，前提成立。**但启动前请用 `route print` 与 CONTROL tag=6 同步下来的 `PeerProxys`/`PXs` 表实际核对一遍**：只要 `PeerProxys` 里出现了 `172.10.0.2`，就说明是同域，此时 D9 方案不成立，必须退回虚服务地址方案（把服务绑到 color0 自己的地址上，见 §2.5）。

### 2.5 虚服务地址（rev.4 起为**采用方案**，D18）

2026-09-21 用户决定采用本方案（D18）。原文写的是「§2.4 第 3 条不成立时的备用方案」，
现在它是默认方案——同域部署时仍然是唯一选择，跨域部署时则是更省事的那个选择：

- 提供端 color0 取 `172.10.9.2/24`，源站 bind `0.0.0.0` 使其同时监听该地址；
- 对外发布 `tcp://172.10.9.2:8000`；
- 消费端路由 `172.10.9.2/32 → color0`（**仍然只允许 /32**：`consumer/config.py` 强制
  这一条，理由见 §2.4 第 1 条。原文这里写的 `/24` 会被配置加载直接拒绝）。

此时内层包目的正是 color0 自己的地址，**四个弱主机开关一个都不需要**（§2.3 的对照实验第一行已实测确认），且服务地址段与 RM/BR/物理地址完全不相交，无环路风险。代价是发布的是虚地址而非物理地址。

> rev.3 起本方案的性价比明显高于 D9：省掉两张网卡上的四个系统级开关、省掉在物理网卡上放宽主机模型带来的攻击面，而契约完全相同、切换只改一个配置项。若不是论述上必须强调「发布的是真实物理地址」，建议直接用本方案。

两套方案只差「服务地址取物理还是取 tun 地址」，其余契约完全相同，配置项也一样，切换成本很低。

### 2.6 环境自检清单

配完环境、起代理之前先过一遍，能省掉大量后续排查：

1. `route print`：确认 `172.10.0.2` 的下一跳是 color0；确认**没有**任何指向 color0 的路由覆盖到 RM、BR、物理地址。
2. **两张网卡**的 weakhost 项都要确认为 enabled——color0 与服务地址所在的那张网卡（§2.3 的实测修正），并确认 color0 的 MTU 为 1280。netsh 的输出是**本地化**的（中文 Windows 打印「弱主机发送 / 弱主机接收」而非 `weakhostsend/weakhostreceive`），按英文键名解析会永远匹配不到，故用与语言无关的：
   ```powershell
   Get-NetIPInterface -AddressFamily IPv4 |
     Select-Object InterfaceAlias, WeakHostSend, WeakHostReceive, NlMtu
   ```
3. **防火墙**：Wintun 适配器在 Windows 眼里是新网卡，NLA 大概率归为「公用网络」，入站几乎全拦。包会被正常投递到 IP 层然后死在 WFP 上，症状和强主机丢弃一模一样。原型阶段先放行：
   ```powershell
   Set-NetConnectionProfile -InterfaceAlias "color0" -NetworkCategory Private
   New-NetFirewallRule -DisplayName "color-tun" -Direction Inbound -InterfaceAlias "color0" -Action Allow
   ```
4. **源站监听地址**：`netstat -ano | findstr :8000` 确认监听在 `0.0.0.0` 或 `172.10.0.2`，只听 `127.0.0.1` 的话包到了也没人收。
5. **提供端 raw socket 必须显式绑到物理地址 `172.10.0.2`**。绑 `INADDR_ANY` 再开 `SIO_RCVALL` 有把自己写进 tun 的内层包也收上来、形成自环的风险。现有 `transport/receiver.py` 按配置的 `ipv4` 绑，且在 `run()` 里额外过滤 `packet.dst != self._bind_ip`，**两道兜底都已就位**，改动时勿动这两处。
6. tun 已创建但代理未启动时，从 C `telnet 172.10.0.2 8000` 应当**不通**（包进了 tun 但没人读，被丢弃）。若通了，说明路由没生效、流量走了物理路径。注意前提是 tun 适配器已存在——适配器没起时主机路由也不存在，这条判据反而会通。

## 3. 服务级 SID（契约）

### 3.1 规范服务串（D12）

```
<proto>://<ipv4>:<port>
```

严格规则，**两端必须逐字符一致**，否则 SHA1 不匹配：

- `<proto>`：小写字面量，取 `tcp` / `udp` 之一。协议必须入串——`tcp://…:21` 与 `udp://…:21` 是两个不同的服务。
- `://`：固定三字符分隔符。
- `<ipv4>`：点分十进制，无前导零（`172.10.0.2`，不是 `172.010.000.002`）。
- `<port>`：十进制，无前导零，**必须显式出现**（含通配的 `:0`，见 §3.3）。
- 全串无空格、无 path、无末尾斜杠，ASCII 编码。

示例：`tcp://172.10.0.2:8000`

**与内容级的哈希域隔离**：内容级 L_sid 的 scheme 恒为 `http`/`https`，服务级恒为 `tcp`/`udp`，两个哈希域按 scheme 天然不相交，不需要额外规则。只要守住两条：服务级串**不得带 path**，内容级串不得用 `tcp`/`udp` scheme。

**归一化的执行点在提供端**：消费端的 IP 与端口直接来自内层包的二进制字段，天然规范，不可能出现前导零；风险全在提供端读 `config.json`（人手写成 `172.010.0.2` 或 `"port": "8000"`）。因此提供端加载配置时必须用 `ipaddress.IPv4Address` 归一化 IP、`int()` 归一化端口，任何一条不合法即**拒绝启动**并指出是哪条服务——这类错误的症状是"SID 永远对不上"，不 fail-fast 会查很久。

### 3.2 SID 组成

```
L_sid = SHA1(规范服务串)        20 字节
N_sid = 提供方 NID              16 字节
SID   = N_sid ‖ L_sid           36 字节 / 72 hex
```

与 v1 完全同构，消费端的 SID 表查询、提供端的 ANN 发布都可原样复用，只换 L_sid 的算法。

### 3.3 通配端口

允许提供端以更粗的粒度发布：

| 发布形式 | 含义 |
|---|---|
| `tcp://172.10.0.2:8000` | 精确服务 |
| `tcp://172.10.0.2:0` | 该 IP 上**全部 TCP 端口** |

消费端查表两级回退：`(proto,ip,port)` → `(proto,ip,0)` → 未命中则丢弃。

通配是为被动 FTP 准备的：数据连接用临时端口，无法逐个发布 SID。**代价是准入的目的粒度退化到主机级**（来源侧校验不受影响，见 §7.3）。如果 FTP server 支持配置被动端口段（如 50000–50100），建议改为按段逐条发布或实现端口区间匹配，比通配整机干净得多。

注意通配是**另一个 SID、另一条隧道**：同时发布 `:21` 与 `:0` 时，FTP 控制连接与被动数据连接分别走两条隧道。rev.3 的回程反推（§7.2）在这种场景下仍然正确——回程 SID 由内层**源端口**决定，与上行严格对称。这是取消 `PeerTun` 学习的额外收益：rev.2 的单键 `PeerTun[内层src]` 在同一消费端开两条隧道时会互相覆盖。

### 3.4 测试向量（两端实现自检用）

**按 D12 的新格式全部重算**，rev.2 的旧向量（无 `://`）全部作废：

| 规范服务串 | L_sid (SHA1, hex) |
|---|---|
| `tcp://172.10.0.2:8000` | `8ae37891ae4a7199ceca8962c12061637ca1f560` |
| `tcp://172.10.0.2:21` | `52ae3dfb6e1b4b01dd67c119c930f4e6ac571e80` |
| `tcp://172.10.0.2:3306` | `92acf1bac92fe6396f990b933a2a8eb3f49f3fd3` |
| `udp://172.10.0.2:5004` | `dfe05b09001a47cce837108c500214c65019da3c` |

### 3.5 消费端不需要明文服务表

沿用 v1 的隐私特性：RM 下发的 SID 表只有 `{L_sid, N_sid}`。消费端从 tun 读到包后，用观察到的 `(proto, dst_ip, dst_port)` **自行拼串并 SHA1**，再拿 L_sid 去表里查 N_sid。全程不需要 RM 下发明文地址。

代价是消费端只能靠路由把候选流量导进 tun，算完哈希才知道命不命中。因此 §2.4 的主机路由要配得精确。

**实现上可直接复用现有表**：`colorproxy/consumer/state.py` 的 `_sid_table` 已经是 `lsid_hex → 完整 SID` 的结构（`lookup_by_url()` 就是这么查的），L3 只需加一个 `lookup_by_service(proto, ip, port)`，不改结构。但要知道它是**单值**的：两个提供端发布同一服务串会得到同一个 L_sid、不同 N_sid，后入表者覆盖先入表者。v1 里这是多源特性，L3 里意味着隧道对端可能在重启后静默切换到另一个提供端。原型单提供端无影响，多提供端时需要显式选源策略。

## 4. 报文格式（契约）

### 4.1 `load[0]` 类型位扩展

v1 用 `WEB_MSG_TYPE_MASK = 0x30`（bit4–5），四个取值已占满。v2 **将掩码扩宽到 `0xF0`（bit4–7）**，v1 的三个取值原样不变，向后兼容：

| `load[0] & 0xF0` | 名称 | 方向 | `load[1:]` | 备注 |
|---|---|---|---|---|
| `0x00` | 文件模式 / 保留 | — | — | v1 已有 |
| `0x10` | `TUNNEL` | P→C | 空 | v1 已有，**L3 模式复用**，用于回送 PID 序列 |
| `0x20` | `HTTP_REQUEST` | C→P | HTTP 请求 | v1 已有 |
| `0x30` | `HTTP_RESPONSE` | P→C | HTTP 响应分片 | v1 已有 |
| `0x40` | **`IP_UPSTREAM`** | C→P | 完整内层 IPv4 包 | **v2 新增** |
| `0x50` | **`IP_DOWNSTREAM`** | P→C | 完整内层 IPv4 包 | **v2 新增** |
| `0x60`–`0xF0` | 保留 | — | — | 未分配 |

**`load[0]` 不是分派判据（D13）。** v1 提供端在 `colorproxy/handlers.py` 的 ACK 路径上已经**刻意取消**了 `load[0]` 的类型校验（提交 `cd9348b`「宽松放行」，注释写明"不再校验 `load[0]` 的 WebMsgType 位"），说明这个字节在真机上曾经对不上。把模式分派押在它上面，等于把整条 L3 上行押在一个已知不可靠的判据上。

因此两端一律**先按 SID 查服务/隧道表决定走哪条路径**（提供端查 `_web_services` / `_l3_services`，消费端查 v1 未决表 / L3 隧道表），`load[0]` 只做一次宽松校验：**不符时照常处理**，只递增 `load0_mismatch` 计数并打 debug 日志。

由此还有一个直接后果：`0x10 TUNNEL` 在 v1 与 L3 之间复用**不产生二义性**——消费端靠"该 SID 在哪张表里"区分，而不是靠这个字节。代价是宽松校验对隧道包没有鉴别力（两种模式都是 `0x10`），这可以接受：SID 已经唯一确定了模式。

代码改动：`colorproxy/protocol/constants.py` 中 `WEB_MSG_TYPE_MASK` 由 `0x30` 改为 `0xF0`，`WebMsgType` 新增两个成员。消费端 v1 的 `load[0]` 判断语句（`consumer/handlers.py:38`）无需改动；提供端 ACK 路径本就没有类型判断，**也不要再加回强校验**（D13）。

### 4.2 `LAST` 位在 L3 模式下的语义

`LoadFlag.LAST (0x01)` 在 L3 模式下**恒置 1**：每个 DATA 自成一个完整数据报，不存在分片序列。

> ⚠️ 必须实现，否则消费端 v1 遗留的哨兵逻辑（收到 LAST 才 `put(None)` 结束）会错乱。两端在 L3 分支中都不得复用 v1 的分片重组路径。

### 4.3 载荷约定

- 一个 DATA 承载**恰好一个**完整内层 IPv4 包，从版本/IHL 首字节开始。
- v2 **不做多包聚合**。（优化方向记录：内层 IP 头自带 Total Length 可自定界，纯 ACK 只有 40 字节而 CoLoR 头有 80–130 字节，头部开销超过 200%，聚合能显著改善。v2 先保持一包一包。）
- 内层包不做任何改写，**MSS clamp 除外**（§6.2）。
- 不支持 IPv6，收到非 IPv4 内层包直接丢弃 + 日志。

### 4.4 报文头字段

与 v1 DATA 完全一致，不新增字段：

| 方向 | 报文 | 关键字段 |
|---|---|---|
| C→P 上行 | `DATA (B=1)` | `NSID/LSID` = 服务 SID；`Destination_NID` = 提供方 NID；`Source_NID` = 消费端 NID；`PID_List` = 反向路径；`SegID` = 隧道 tx |
| P→C 下行 | `DATA (B=0, R=1 跨域)` | `NSID/LSID` = 服务 SID；`Destination_NID` = 消费端 NID；`PID_List` = GET 累积的 PID + 末尾保留 PID(0) |

## 5. 状态机（契约）

```
消费端 C (NID_C, color0 10.99.1.1)                      提供端 P (NID_P, 服务 172.10.0.2)
        │                                                          │
        │  客户端首个包到达 color0，算出 SID，无隧道 → 缓存该包      │
        │                                                          │
   ① ── GET(NSID=NID_P, LSID=SHA1(服务串), nid=NID_C,              │
        │       S=1, SegID=tx, 无 payload) ──────────────────────▶ │  查 _l3_services 命中（D13）
        │                          (RM/BR 沿途累积 PID)             │  记 L3Tunnel[(SID,NID_C)] =
        │                                                          │    {return_ip, pids, random_num, SegID}
        │                                                          │
   ② ◀── DATA(B=0, load=[0x10|LAST], 空载, PIDs=回址) ─────────────│  与 v1 完全相同的隧道 DATA
        │  C 提取 PID 序列 → Tunnel[SID] = {rev_pids, NID_P, next_hop_ip}
        │  冲刷首包队列                                              │
        │                                                          │
   ③ ── DATA(B=1, load=[0x41] + 内层IP包) ──────────────────────▶ │  逐包准入校验（dst 三元组 +
        │                          × N，持续                        │  src 绑定），write(color0)
        │                                                          │
   ④ ◀── DATA(B=0, load=[0x51] + 内层IP包) ───────────────────────│  read(color0) 得回程包，由内层
        │                          × N，持续                        │  src 三元组反推 SID，封装发出
```

与 v1 的关键差异：

- ①② 只在**每条 SID 的第一个包**时发生一次。按 D1，此后隧道长期有效，不再重新握手、不刷新、不回收。
- ③④ 是**双向持续的数据流**，不是一问一答。同一 SID 上的所有 TCP 连接共用这一条隧道。

### 5.1 「CoLoR 没有端口如何区分多流」的正面答案

**不需要区分。** 隧道以 SID 为单位而非以流为单位，同一 `(proto, ip, port)` 的所有连接共用一条 PID 隧道，**内层 IP/TCP 头天然完成解复用**。两端都只维护每 SID 一条隧道记录，不维护五元组流表（流缓存仅为性能优化，见 §7.1）。

### 5.2 首包缓冲

隧道未建立时到达的包：**按 SID 各自入队**，每条 SID 上限 **4 个包或 8 KB**（先到先出，超限丢弃最老的）。隧道建立后按序冲刷。

不缓冲也能工作（客户端 SYN 会在约 1 s 后重传），缓冲只是省掉这一秒。但**必须实现"隧道建立失败后丢弃队列并记日志"**，否则首包会永久滞留。

握手超时：发出 GET 后 `TUNNEL_TIMEOUT`（建议 5 s）未收到 ②，丢弃队列、记 warning、把该 SID 标回未建立状态，下一个包会重新触发 GET。

## 6. MTU 与 MSS（契约）

### 6.1 预算核算

下表是用 `colorproxy/protocol/packets.py` 实际构建报文量出来的（取 `Header_Length` 字段的真实值），不是估算。rev.2 的旧表漏算了 `Source_NID` / `HMAC` / `Segment_ID` / 尾部保留 PID 四项：

```
外层开销 = 外层IP(20) + CoLoR 头(Header_Length) + load[0](1)

CoLoR 头 = 基础(10) + NSID(16) + LSID(20) + Destination_NID(16)
         + Source_NID(16，B=1 上行 或 B=0&R=1 下行，两者都占)
         + HMAC(4，C=1) + Segment_ID(4，S=1，现有实现恒置)
         + PID 序列(4 × PID 数；下行含尾部保留 PID)
```

| 方向 | 标志 | 跳数 | CoLoR 头 | 外层总开销 | 可用内层 |
|---|---|---|---|---|---|
| 下行 | `B=0,R=1,C=1,S=1` | 8 | 122 | 143 | 1357 |
| 下行 | `B=0,R=1,C=1,S=1` | 16 | 154 | 175 | 1325 |
| 上行 | `B=1,S=1` | 8 | 114 | 135 | 1365 |
| 上行 | `B=1,S=1` | 16 | 146 | 167 | 1333 |
| 上行 | `B=1,S=1,C=1` | 8 | 118 | 139 | 1361 |

（rev.2 写的是下行 115 / 上行 131，下行漏 28 字节、上行漏 4 字节。上行是否带 `C=1` 取决于 §8.5 第 1 问的答案。）

PID 跳数是变量，**隧道建立之前不知道**。因此：

> **两端 tun MTU 固定 1280。** 该值同时是 IPv6 最小 MTU，且低于 QUIC 的 1200 字节探测门限。实测余量可覆盖**下行 27 跳 / 上行 28 跳**（下行第 28 跳时外层达 1503 > 1500）。

### 6.2 MSS clamp（两侧都要做）

内层 TCP 不知道隧道 MTU，必须改写握手包里的 MSS 选项：

- **消费端**：对客户端发出的 `SYN` 改写 MSS → **1240**（= 1280 − 20 IP − 20 TCP）。
- **提供端**：对服务端发出的 `SYN-ACK` 改写 MSS → **1240**。

> ⚠️ **只做一侧会导致服务端往回发大包时形成黑洞**，表现为"连接建立了、小请求正常、一传大数据就卡死"，排查代价很高。两侧都必须实现。

实现：扫描 TCP options 找 `kind=2, len=4`，把 16 位 MSS 值改小（**只减不增**），然后重算 TCP 校验和（可用增量更新）。若 SYN 中没有 MSS 选项则不处理（对端会用 536 的默认值，安全）。

> **rev.4 实情补充：在 D3 拓扑下这两处 clamp 多半是空操作，别据此判断它没生效。**
> 客户端的 SYN 与源站的 SYN-ACK 都是内核按 tun 的 MTU(1280) 发出的，内核自己就会填
> `MSS=1240`，clamp 只减不增，于是什么也不改，`mss_clamped` 计数器停在 0。这**不是**
> 故障。clamp 真正兜的是另外几种情形：tun MTU 没配对、内层包来自别的主机（开了 IP
> 转发）、对端实现按 1460 硬填。判据应当是「观察到的 MSS ≤ 1240」，而不是「clamp
> 改写过字节」——`tools/l3_m1c_loopback.py` 的报告按这个措辞分开打印两件事。

### 6.3 UDP 与超长包

先澄清一件 rev.2 判断错了的事：

> **按 D3（客户端与代理同机），代理几乎不会从 tun 读到超过 1280 的包。** 内层流量全部由本机应用产生，内核在写入 color0 之前就已按接口 MTU 处理完了：`DF=1` 的（QUIC 等）`sendto` 直接返回 `WSAEMSGSIZE`，由应用自己退避；`DF=0` 的由内核自行分片。要触发"代理读到超长包"，得开 IP 转发、替别的主机转发流量——D3 已排除这种拓扑。

| 情况 | 处理 | 优先级 |
|---|---|---|
| 内层包 ≤ 1280 | 正常转发 | — |
| 内层包 > 1280 且 `DF=1` | 丢弃 + `mtu_drop` 计数；**可选**本地构造 `ICMP 3/4 (Next-Hop MTU=1280)` 写回 tun | **降级（D16）**：防御性实现，不进 M3 关键路径 |
| 内层包 > 1280 且 `DF=0` | 正常转发（内核已按 tun MTU 分片，代理侧不再分片） | — |

**真正会咬人的是内层分片，不是超长包。** 内核按 tun MTU 1280 分片之后，**非首片没有 TCP/UDP 头**，两端的端口提取与准入校验都会失败。症状恰好就是 rev.2 在这一节警告的"小包通、大 UDP 静默丢"，但成因完全不同，照 rev.2 的思路排查会一直查错方向。处理见 §7.1 第 3 步（D15）。

> D11 与本节的区分仍然成立：**D11 说的是「不隧道传输 ICMP」，不是「不产生 ICMP」。** 本节的 ICMP 由代理在本地构造、写回本地 tun、不进 CoLoR。只是它的触发条件在 D3 拓扑下近乎为零，故降级为防御性实现。

QUIC 用 DF=1 并自行探测，收到 ICMP 或探测失败后会退到 1200，能正常工作。

## 7. 数据面处理（契约级行为）

### 7.1 消费端

**上行（color0 → CoLoR）**

1. 从 color0 读一个完整 IP 包，校验 `version==4`（非 IPv4 → 丢弃 + `nonipv4_drop`）。
2. 取 `proto`；`proto ∉ {6,17}` → **丢弃 + `proto_drop` 计数**（D11：ICMP 等非 TCP/UDP 不进隧道）。
3. **分片检查（D15）**：读 IP 头的 `Flags/Fragment Offset` 字段，**`MF==1` 或 `Fragment Offset != 0` 一律丢弃 + `frag_drop` 计数 + 限速 warning**，不做重组。
   - 非首片没有传输层头，取不出端口，算不出 SID；首片虽然能算出 SID，但后续片必被丢弃、收端无法重组，**只发首片纯属浪费带宽**，故两者同等处理。
   - 硬约束（必须写进部署说明）：**内层 UDP 数据报净载荷须 ≤ 1252 字节**（1280 − 20 IP − 8 UDP）。RTP/RTCP 默认远小于此值；编码器若可配 MTU，配 1200 更稳。
   - TCP 侧由 MSS clamp（§6.2）保证不触发分片，这一步对 TCP 是纯兜底。
4. 从 `ihl*4` 偏移取 `dst_port`。
5. 查**流缓存** `(proto, dst_ip, dst_port) → SID | MISS`。未命中缓存则拼规范串（§3.1）、SHA1、查本域 SID 表（含 §3.3 两级回退），结果写回缓存。
   - 流缓存是必需的性能措施，否则每包一次 SHA1 + 字典查询。
6. `MISS` → 丢弃 + `sid_miss` 计数。
7. TCP `SYN` → MSS clamp（§6.2）。
8. 隧道已建立 → 封 `DATA(B=1, load=[0x41] + 内层包)`，发往 `next_hop_ip`。
9. 隧道未建立 → 入首包队列 + 发 GET（§5.2）。

**下行（CoLoR → color0）**

1. 收到 `B=0` 的 DATA，**按 SID 查本端表分派**（D13）：命中 L3 隧道表则走本路径，命中 v1 未决表则走 v1 路径，两表皆无则丢弃 + 计数。
2. `load[0]` 宽松校验应为 `0x50`，不符**照常处理**、只计 `load0_mismatch`。取 `load[1:]`。
3. 校验内层 `dst_ip == color0 地址`，不符则丢弃 + 日志（防对端串流）。
4. 原样 `write(color0)`。

**收到 `0x10` TUNNEL** → 该 SID 在 L3 待建表中时，按 §5 存隧道、冲刷首包队列；在 v1 未决表中时走 v1 路径（判据是表，不是 `load[0]`，见 §4.1）。

### 7.2 提供端

**注入方向（收到上行 → 交本机协议栈）**

1. 收到 `B=1` 的 DATA，还原 SID 与 `Source_NID`（消费端 NID，记作 `NID_C`）。
2. **按 SID 分派（D13）**：命中 `_l3_services` 走本路径；命中 `_web_services` 交 v1 路径；两表皆无则丢弃 + 计数。`load[0]` 宽松校验应为 `0x40`，不符只计 `load0_mismatch`。
3. 查 `L3Tunnel[(SID, NID_C)]`，缺失则丢弃 + `no_tunnel_drop`。
4. 取出内层包，校验 `version==4`、`proto ∈ {6,17}`，并按 §7.1 第 3 步做同样的分片检查（`MF==1 || offset!=0` → `frag_drop`）。
5. **准入校验（强制，见 §7.3）**，两条都要过：
   - **目的**：内层 `(proto, dst_ip, dst_port)` 必须与该 SID 绑定的服务一致（通配端口时只比 `proto` + `ip`）。不符 → 丢弃 + `admit_drop` + warning。
   - **来源**：内层 `src_ip` 必须等于 `peers[NID_C].tun_ip`（§9.1 静态配置）。不符 → 丢弃 + `src_bind_drop` + warning。
6. TCP `SYN` → MSS clamp 兜底。
7. `write(color0)`。

> rev.2 的「`PeerTun[内层 src_ip] = (SID, NID_C)`，首次出现时建立」**已删除**（D14），理由见 §7.3。

**回送方向（本机回程 → 发回消费端）**

1. 从 color0 读一个完整 IP 包，校验 `version==4`、`proto ∈ {6,17}`，分片检查同上。
2. **由内层源三元组反推 SID**：`SID = 查表(SHA1("<proto>://<src_ip>:<src_port>"))`，未命中则按 §3.3 回退到 `<proto>://<src_ip>:0`；仍未命中则丢弃 + `sid_miss`。
   - 这就是消费端当初拿来作**目的**的那个服务串，与 §7.1 的上行严格对称。
   - 查的是提供端自己的 `_l3_services`（本机发布的服务，含通配项），**不依赖任何数据面学习**。
3. **由内层目的地址定消费端**：`NID_C = peers_by_tun_ip[内层 dst_ip]`，未命中则丢弃 + `no_peer_drop`。
4. 查 `L3Tunnel[(SID, NID_C)]` 得 `{return_ip, pids, random_num}`，未命中则丢弃 + `no_tunnel_drop`。
5. TCP `SYN-ACK` → MSS clamp（§6.2）。
6. 封 `DATA(B=0, R=1, C=1, load=[0x51] + 内层包)`，填 HMAC（种子 = 该隧道的 `random_num`），发往 `return_ip`。

第 2、3 步各需要一张表，两张都是**静态**的：`_l3_services`（SID → 服务，ANN 发布时建立）与 `peers_by_tun_ip`（tun_ip → NID，配置加载时建立）。**数据面不写任何表。**

### 7.3 §7.2 第 5 步是本方案最重要的安全点

L3 隧道化以后有两个方向的边界，**都必须逐包校验**。

**目的方向**：如果不校验内层目的地址与 SID 的绑定关系，**任何持有一条 SID 的消费端都能借这条隧道把流量打到提供端可达的任意地址和端口**。「ip+端口粒度的内容管控」真正落地的地方就是这一行校验，而不是握手时的那一次 SID 查表——握手只证明"你有权建这条隧道"，逐包校验才证明"你发的每个包都在这条隧道允许的范围内"。

在 D9 方案下这一点尤其要紧：弱主机模型开启后，提供端对内层包的投递范围扩大到了**本机全部网卡地址**，准入校验是唯一的边界。

**来源方向（rev.3 新增，D14）**：rev.2 用 `PeerTun[内层 src_ip] = (SID, NID_C)` 从数据面学习回程表项，且不校验该源地址是否真属于这个消费端。两个后果：

- **回程劫持**：持有任意一条 SID 的消费端，只要发一个内层 `src` 伪造成 `10.99.1.2` 的包，就能改写受害者的回程表项，把别人的回程流量引到自己这条隧道；写成"首次出现时建立"则变成先到者永久占位，即拒绝服务。§2.2 原先只要求"tun 地址全局唯一"，没有任何强制手段。
- **通配 SID 串台**：按 §3.3 同时发布 `:21` 与 `:0` 时是两条隧道，而同一消费端两条隧道的内层 `src` 是同一个地址，单键 `PeerTun` 会互相覆盖，回程包可能从错误的隧道发出。

rev.3 的处理是**取消学习**，而不是给学习打补丁：

1. 回程 SID 由内层**源**三元组反推（§7.2 回送第 2 步）——与上行对称，通配场景天然正确；
2. 消费端身份由内层**目的**地址查静态 `peers[]`（§9.1）；
3. 入向增加"内层 `src` 必须等于该 NID 绑定的 tun 地址"（§7.2 注入第 5 步）。

于是数据面**不再写任何表**，控制面（ANN 发布 + 配置加载 + 握手）成为唯一的表写入方。这同时让 §2.2 的"每个消费端 tun 地址全局唯一"从一句约定变成了一条可执行的校验。

## 8. 边界、限制与已知风险

### 8.1 结构性不支持

| 项 | 原因 | 备注 |
|---|---|---|
| **服务端主动发起的连接** | CoLoR 是拉驱动，提供端无法主动建隧道 | **主动模式 FTP 不通**（被动模式通）；RTP 回流、P2P 同理 |
| DNS | D4 原型不设计 | 直接用 IP |
| ICMP 隧道传输 | D11 | 见 §8.2 |
| IPv6 内层包 | v2 不支持 | 丢弃 + 日志 |
| **内层 IP 分片** | D15 不做重组 | 丢弃 + `frag_drop`；内层 UDP 净载荷须 ≤ 1252 字节，见 §7.1 第 3 步 |
| 网内缓存 | 字节流不可缓存 | 见 §0.2 |

### 8.2 ICMP 不做隧道传输（D11）

**可以不做，结论是安全的。** 需要区分三件事：

| | 是否实现 |
|---|---|
| 隧道传输应用发起的 ICMP（`ping 172.10.0.2` 等） | **不实现**。消费端在 §7.1 第 2 步直接丢弃 |
| 代理本地产生的 `ICMP 3/4`（PMTUD，§6.3） | **可选（D16 已降级）**。不进 CoLoR，只写回本地 tun；D3 拓扑下近乎不触发 |
| 代理本地产生的 `ICMP 3/1`（SID 未命中告知本机应用） | 可选。不做则应用会干等到自身超时 |

代价只有一个，但值得提前知道：**失去了最省事的联调判据**。原来"`ping` 通了说明隧道通"一步就能把 CoLoR 链路和上层问题分开，现在最小连通性测试要改成 TCP：

```powershell
# 提供端起一个最小监听
python -m http.server 8000 --bind 0.0.0.0
# 消费端
Test-NetConnection 172.10.0.2 -Port 8000     # 只看 TCP 三次握手是否完成
```

TCP 握手涉及 MSS clamp 与双向隧道，故障面比 ICMP 大。如果 M2 阶段卡住，建议临时加一个 `debug_tunnel_icmp: true` 开关放行 ICMP 用于定位，跑通后关掉即可。这个开关的实现成本只有几行（§7.1 第 2 步放行 `proto==1`，端口按 0 处理）。

### 8.3 准入粒度的实际下限

被动 FTP 必须用通配端口发布（§3.3），**目的侧**准入粒度实际退化到主机级。这是 FTP 协议本身的性质，不是方案缺陷，但要在论述中写明。若 FTP server 可配置被动端口段，优先按段发布。

需要同时说清的是**来源侧不退化**：§7.2 的 `src` 绑定校验与端口粒度无关，通配只放宽"能打到本机哪个端口"，不放宽"谁能打进来"。

### 8.4 D1（隧道长期有效）的风险与最小兜底

按 D1 不做刷新与回收。需要接受的后果：**提供端重启、RM/BR 路径状态变化、BR 侧 PID 表老化，都会让隧道静默失效，且没有任何恢复路径**，表现为"跑着跑着就断了，重启消费端才好"。

建议留两个成本极低的兜底，默认关闭，联调不顺时打开：

```json
"tunnel_refresh_sec": 0      // 0 = 关闭（D1 默认）；>0 = 每 N 秒重发 GET 刷新 PID
"tunnel_redetect_sec": 0     // 0 = 关闭；>0 = 上行活跃但下行静默超过 N 秒则重发 GET
```

重建时新旧 PID 路径原子替换，旧路径宽限 2 s 给在途包。

### 8.5 待与 RM/BR 团队确认的四件事

1. **上行 `B=1` DATA 是否需要携带 HMAC？** v1 消费端 GET/ACK 都不带 HMAC，因为上行只有一个包。L3 模式下上行是持续大流量，如果 BR 对上行做 HMAC 校验，消费端必须补上生成逻辑。
2. **`Random_Num` 种子长期复用是否可行？** v1 一次事务一个种子，L3 下同一个种子要用在这条隧道的全部下行包上。
3. **BR 的 PID 路径是否真的长期有效、有无老化时间？** 直接决定 D1 能否成立、§8.4 的兜底要不要默认打开。
4. **单条 SID 有无速率或 pps 限制？** 视频流场景下可能撞限。

`weak_host: true` 时进程启动检查 netsh 开关是否已开，未开则打印告警与命令（不自动改
系统配置）。**采用 D18 后这项检查会自行跳过**：实现会比对 `l3.services[].ip` 与
`l3.tun_ip`，服务全部绑在 tun 自己身上时内层包目的正是收包网卡自己的地址，强主机模型
天然满足，此时打印一行 info 说明而不告警。

> **rev.4 勘误：`tunnel_refresh_sec` 放在提供端这一段是笔误。** §8.4 给它的语义是
> 「每 N 秒重发 GET 刷新 PID」，而 GET 只有消费端会发，提供端拿它无事可做。实现的是
> 消费端 `l3.tunnel_redetect_sec`（§9.2），提供端配置里若填了非 0 值，启动时会打印
> 一行告警指向正确的那个配置项——留着静默不生效会让人以为兜底开着。

**`peers[]` 是 rev.3 新增的必填项（D14）**，承担两件事：

1. 提供 `NID → tun_ip` 映射，供 §7.2 注入方向的**来源校验**使用；
2. 提供反向的 `tun_ip → NID` 映射（加载时建立 `peers_by_tun_ip`），供 §7.2 回送方向定位消费端。

加载时校验：`tun_ip` 两两不重复（重复即拒绝启动，这正是 §2.2「全局唯一」的落地点）、都落在 `peer_routes` 覆盖的网段内、都不等于本机 `tun_ip`。`peers[]` 为空时 L3 模式不可用，应拒绝启动而不是静默丢包——否则症状是"隧道建得起来但一个包都过不去"。

`l3.services[]` 的每一项在加载时按 §3.1 归一化并算出 SID，登记进 `_l3_services`，同时发 ANN（与 `services[]` 的 web 服务各走一张表，D13）。

### 9.2 `config-consumer.json` 新增 `l3` 段

```json
{
  "nid": "<32hex>",
  "ipv4": "10.10.0.2",
  "rm_ipv4": "10.10.0.1",
  "proxy_port": 8910,

  "l3": {
    "enabled": true,
    "tun_name": "color0",
    "tun_ip": "10.99.1.1",

    "mss_clamp": 1240,
    "capture_routes": ["172.10.9.2/32"],
    "static_services": [
      { "proto": "tcp", "ip": "172.10.9.2", "port": 8000,
        "provider_nid": "<提供方 32hex>", "desc": "SID 表未就绪时的降级路径" }
    ],
    "tunnel_timeout_sec": 5.0,
    "firstpkt_queue_pkts": 4,
    "firstpkt_queue_bytes": 8192,
    "tunnel_redetect_sec": 0,
    "debug_tunnel_icmp": false
  }
}
```

`capture_routes` **只写 `/32` 主机路由**，理由见 §2.4。进程启动时校验：每条 capture_route 都不得包含 `rm_ipv4`，同步到 `PeerProxys`/`PXs` 后再校验一次，命中则拒绝启动并打印原因。

消费端**不需要**静态服务列表：它从 tun 观察到目的地址后自行拼串算 L_sid，再查 RM 下发的 SID 表拿 N_sid（§3.5）。

`static_services[]` 是 SID 表未就绪时的降级路径，**rev.4 起已实现**（在此之前它只是一句设计文字，`_preload_static_sids` 只认 URL；没有 RM 的环境里消费端拿不到服务级 SID，每个包都 `sid_miss`，L3 一步也走不动）。它与 `sids[]`（内容级，按 URL）并列而不合并：两者的 L_sid 算法不同（`SHA1(url)` vs `SHA1("<proto>://<ip>:<port>")`），混在一个列表里只会让人写错哪一种。加载时按 §3.1 归一化并 fail-fast——算错一个字节的症状是"SID 永远对不上"，而两端配置看着都对。

`tun_ip` 必须与提供端 `peers[]` 里为本消费端 NID 登记的地址**逐字节一致**（D14）：不一致时隧道能建起来、上行也发得出去，但每个包都会在提供端的来源校验上被 `src_bind_drop` 拦掉。这是 rev.3 引入的新的"两份配置必须对齐"约束，与 §9.3 第 1 条同类，部署清单里要单列一行。

### 9.3 顺带修掉的 v1 配置问题

上一轮已指出，L3 模式同样受影响，一并处理：

1. 两份配置的网段对不上（`172.10.0.x` vs `10.0.1.5` / `10.135.147.229`），静态 SID 预载的 URL 与提供端发布的 URL 哈希不同，永远匹配不上。本文按 D5 统一为 `10.10.0.2` / `172.10.0.2`。
2. `config.json` 中 `/api/items` 的 origin 指向了 `172.10.0.5:8000`（RM 那台机器），其余三条指向 `172.10.0.2`。应改回 `172.10.0.2`。
3. 注册只在启动时做一次（3 次重试），RM 重启后不会重新注册也不重发 ANN。L3 模式下隧道长期有效意味着暴露窗口更长，**必须改成常驻注册线程**。
4. CONTROL `tag=8`（新代理通知）未处理，后启动的一方学不到先启动方的 NID→IP。

### 10.2 Windows：用 Wintun（D7）

**是的，Windows 上用 Wintun。** 三个候选的对比：

| | 层次 | 说明 |
|---|---|---|
| **Wintun** ✅ | L3 | WireGuard 项目出品，签名驱动，性能好，无独立安装程序——`wintun.dll` 自带驱动，进程内创建适配器 |
| tap-windows6 | L2 | OpenVPN 的老驱动。二层设备，要自己处理 ARP/以太头，还要单独装驱动包。不用 |
| WinDivert | 非 tun | 按过滤表达式截获包，消费端侧其实比 tun 更顺手（不用配路由、无环路风险），但与 Linux 的 `/dev/net/tun` 完全不共用代码。跨平台目标下不选 |

Wintun 使用要点：

- 需要**管理员权限**，`wintun.dll` 与主程序同目录，Python 侧用 `ctypes` 直接调即可。
- API 流程：`WintunCreateAdapter` → `WintunStartSession` → 读用 `WintunReceivePacket` + `WintunGetReadWaitEvent`（阻塞事件驱动）→ 写用 `WintunAllocateSendPacket` + `WintunSendPacket`。基于环形缓冲，零拷贝。
- **适配器创建后不会自动配 IP**，需要用 `netsh interface ip set address` 或 IP Helper API 单独配地址与 MTU。
- 读是阻塞事件驱动，**单独一个线程读**，投递到发送队列，不要和 CoLoR 收包线程混在一起（§1.2/§1.3）。
- 启动顺序：创建适配器 → 配地址/MTU → 配路由 → 开弱主机开关（提供端）→ 放行防火墙 → 再开始收发。退出时删除适配器与路由。

Linux 侧后续用 `/dev/net/tun` + `TUNSETIFF|IFF_TUN|IFF_NO_PI`，语义与 Wintun 一致（都是纯 L3、无以太头），`ipv4.py` / `mss.py` / `l3/` 全部可共用，只有 `device_*.py` 不同。

### 10.3 性能（视频流必须提前处理）

视频是逐包转发，量级和 HTTP 的几十个分片完全不同。现状用 scapy 收发，每包几十微秒，几千 pps 就到顶（5 Mbps 视频约 500 pps 能扛，50 Mbps 不行）。

必做：

1. **数据面彻底去 scapy。** 每条隧道预生成 CoLoR 头模板（`bytes`），发包时 `模板 + 内层包`，只用 `struct` 回填长度、校验和、HMAC，走 raw socket `sendto`。注意 §2.4 第 2 条：改 raw socket 后必须显式指定源地址/接口。
2. 收包先 `raw[9] == 150` 粗筛再解析，用 `memoryview` + `struct.unpack_from`，不构造对象。
3. **现有的"收包回调在接收线程里同步执行"必须改成队列 + 转发线程池**，否则丢包会很严重。
4. **逐包 MD5 HMAC 要实测。** v1 一次事务算几十次，L3 下是每包成本，可能比封包本身还贵。

Python 优化到位大致能到几十 Mbps，做研究演示够用。要跑高码率视频吞吐需要把数据面挪到 C/Rust 或 eBPF，越早决定越好。

### 10.4 可观测性

L3 模式的故障大多表现为静默丢包，没有计数器几乎无法定位。两端各加一个计数器快照（每 5 s 一行）：

```
tun_rx / tun_tx / sid_hit / sid_miss / tunnel_up
/ colr_tx / colr_rx / admit_drop / src_bind_drop / no_peer_drop
/ frag_drop / mtu_drop / no_tunnel_drop / nonipv4_drop / nonunicast_drop / proto_drop
/ load0_mismatch
```

最高频的几个及其含义：

| 计数器 | 含义 | 最可能的原因 |
|---|---|---|
| `admit_drop` | 目的准入校验失败 | 发布的服务与实际访问的 ip:port 不一致 |
| `src_bind_drop` | 内层源地址与 `peers[]` 不符 | 消费端 tun 地址配错，或 `peers[]` 漏配 |
| `no_tunnel_drop` | 回程查不到隧道 | 隧道已静默失效（§8.4），或 `peers[]` 与 NID 对不上 |
| `sid_miss` | 算出的 SID 不在表中 | 路由把不该进的流量导进了 tun；回送方向则是源服务未发布 |
| `frag_drop` | 内层包被分片（D15） | 内层 UDP 数据报超过 1252 字节，见 §7.1 第 3 步 |
| `nonunicast_drop` | 本机往 tun 上发的广播/组播 | **正常现象，不用管**。新建的 tun 上 mDNS/SSDP/NetBIOS/IGMP 每秒好几个。rev.4 起单独计数：混进 `sid_miss` 会把"路由配宽了"这个诊断彻底淹掉（M1c 真机一次 7 秒的运行里 20 个 `sid_miss` 全是噪声） |
| `load0_mismatch` | `load[0]` 类型位与 SID 所属模式不符 | 对端实现的 `load[0]` 与本文不一致；**不影响转发**，只作诊断（D13） |

## 12. 与 v1 的关系

| 能力 | v1 HTTP 模式 | v2 L3 模式 |
|---|---|---|
| 入口 | HTTP 正向代理 :8910 | tun 设备 + 主机路由 |
| L_sid | `SHA1(去 query 的 URL)` | `SHA1("<proto>://<ip>:<port>")` |
| 承载 | HTTP 字节流分片 | 完整内层 IPv4 包 |
| `load[0]` | `0x10 / 0x20 / 0x30` | `0x10 / 0x40 / 0x50` |
| 可靠性 | 无（best-effort，已知风险） | 由内层 TCP 负责 |
| 端到端 TCP | 断开 | 保持 |
| 网内缓存 | 可 | 不可 |
| 握手次数 | 每请求一次 | 每 SID 一次（长期有效） |
| 准入校验 | 握手时查表一次 | **逐包双向校验**（§7.3） |

两个模式在同一进程内共存，**按 SID 所属的服务表分派**（D13，不是按 `load[0]`），互不干扰。提供端可以同时发布 web 类型与 l3 类型的 SID。
