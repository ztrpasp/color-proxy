# 共生网络（CoLoR）技术要点 —— 面向新终端（Web 代理）开发

> 本文从《共生网络技术文档.docx》《共生网络包格式.docx》与参考实现 `color-agent-plus`
> 中提炼**与新终端（基于共生网络的无感知跨域 Web 获取）开发直接相关**的概念、报文与机制，
> 便于开发者快速建立背景、不必通读全部原始资料。完整定义以原始 docx 为准。

## 1. 共生网络是什么

共生网络（CoLoR）是一种**数据/服务导向**的新型网络体系，强调内生安全与可控可信。
它不以"主机到主机的 IP 连接"为中心，而以"获取某个**服务/内容**"为中心：请求者声明
要的是哪个服务（用 SID 标识），由网络负责把请求路由到能提供该服务的节点，并把数据沿
**最短路径反向**送回。其安全性来自三维标识体系中的哈希绑定与逐跳路径校验。

CoLoR 报文承载在 IP 之上，使用 **IP 协议号 150**，报文版本号 **Version = 7**。

---

## 2. 三维标识地址空间（核心）

| 标识 | 长度 | 含义 | 终端开发相关性 |
|---|---|---|---|
| **NID** 节点标识 | 128 bit / 16 B | 节点唯一标识，= 节点公钥的哈希；用于节点身份认证 | 每个终端有一个 NID；请求方/提供方都用 NID 标识 |
| **SID** 服务标识 | 288 bit / 36 B | `N_sid(128b) ‖ L_sid(160b)`。N_sid = 提供方 NID（用于路由 + 提供方认证）；L_sid = 内容哈希（用于内容真实性校验） | **Web 服务的 URL 映射为 SID**：`L_sid = SHA1(去 query 后的 URL)`，`N_sid = 提供方 NID` |
| **PID** 路径标识 | 32 bit / 4 B（每跳一个） | 由 RM/BR 在转发时累积，记录最短转发路径，供数据**反向沿原路返回**与逐跳校验 | 即"跨域通信隧道"：请求端拿到合法 PID 序列才能把数据推向提供端 |

> SID 在内存中统一用 **72 位十六进制字符串**表示：`N_sid(32 hex) ‖ L_sid(40 hex)`。

---

## 3. 网络组件与域

- **终端代理（Proxy）**：用户侧软件，封装应用流量进出共生网络。可同时是**消费端**（发起请求）
  与**提供端**（发布并提供服务）。**新终端就是一种 Web 代理形态的终端代理。**
- **资源管理器（RM）**：每个自治域一个，负责终端注册、服务通告（ANN）处理、名字解析与
  域内路由、向终端下发"本域可访问信息"。**需求不变，不在本项目改动范围。**
- **边界路由器（BR）**：连接不同域，转发跨域 CoLoR 包，拦截非法入域/出域包。**需求不变。**

域内通信只经 RM/本域；跨域通信经 BR。终端通过 PID 序列里携带的 **PX**（PID 前缀，高 16 位）
识别应送往哪个 BR。

---

## 4. 通信模型：先拉后推（关键设计前提）

CoLoR 是**先拉后推**：请求方先发 **GET**（拉，不带 payload），提供方再**推送 DATA**（数据）。
整体可分三阶段：

1. **服务通告/注册**：提供方用 **ANN** 把服务（SID）通告给 RM；RM 建立"SID → 提供方"的解析信息。
2. **名字解析（请求路由）**：消费方发 **GET**（携带 SID 与自身 NID），经 RM/BR 路由到提供方；
   **沿途 RM/BR 把 PID 前缀累积到 GET 尾部**，形成到达提供方的最短路径记录。
3. **数据返回**：提供方据 GET 携带的 PID 序列，把 **DATA** 沿**反向路径**送回消费方。

> **对 Web 的影响（本项目核心难点）**：HTTP 是双向的，消费端需要把 HTTP 头+body **主动推**给
> 服务端；而 CoLoR 的 GET 不带 payload。解决办法见 §7。

## 5. 四类报文（与终端相关的关键字段）

报文首字节 = `(Version<<4) | Type`。**字节序约定**：长度/SegID/PID/MTU 等为**小端**；
校验和为**大端**（16 位反码和）；NID/SID 为定长字节数组。

### 5.1 ANN 通告报文（Type=1，首字节 0x71）
提供方 → RM，发布可被访问的服务。携带若干**通告单元（Announce Unit）**，每个单元含
`N/L/I` 标志（是否携带 NSID/LSID/NID）、`AM`（动作：1 注册/2 更新/3 注销）、SID 字段与可选策略单元。
- 终端开发：发布一个 Web 服务 = 构造一个通告单元（N_sid=本机 NID，L_sid=SHA1(去 query 后的 url)）发给 RM。

### 5.2 GET 请求报文（Type=2，首字节 0x72）
消费方发出，**不带 payload**。关键字段：`NSID`/`LSID`（请求的 SID）、`NID`（请求者）、
`MTU`、`PID_List`（沿途累积的路径）、可选 `Segment_ID`、`Flags`（位序 `rCRASQKF`）。
- 终端开发：提供端收到 GET → 还原 SID、取请求者 NID 与 PID 序列 → 据此确定回送地址。

### 5.3 DATA 数据报文（Type=3，首字节 0x73）
提供方 → 消费方推送数据；**ACK 是 DATA 的子类型（B=1）**。关键字段与标志（位序 `rSCQMRBF`）：

| 字段/标志 | 含义 |
|---|---|
| `B` | 1=ACK 确认报文，0=普通数据报文 |
| `R` | 1=经跨域/反向路径（PID 序列末尾附保留 PID） |
| `Header_Length` | 包头长度（自描述，便于 BR 定位 PID 序列）|
| `PID_Pointer` | 指向当前需 BR 校验/使用的 PID |
| `PID_List` | 路径标识序列（小端，每个 4 B） |
| `Destination_NID` / `Source_NID` | 目的/源节点 NID。**B=0**：Destination=消费方，R=1 时再带 Source=提供方；**B=1（ACK）**：含**两个 NID**（Destination=提供方、第二个=消费方） |
| `Segment_ID` | 分段/事务标识（小端） |
| `load` | 负载（紧跟包头之后） |

> **重要实现事实**：DATA 的**校验和仅覆盖包头**（`data[0:Header_Length]`），不含 load；
> 而 GET/ANN/CONTROL 的校验和覆盖整包。

### 5.4 CONTROL 控制报文（Type=4，首字节 0x74）
终端↔RM/BR 的注册与信息同步。头部固定 8 字节：`首字节|TTL|Checksum(2,大端)|Header_Length(8)|Subtype|DataLength(2,小端)`。
本项目用到两个子类型：
- **Subtype=5 注册请求**（终端→RM）：负载 = 本机 IP(4 B 小端) + 本机 NID(16 B 大端)。
- **Subtype=6 域内同步**（RM→终端）：负载 = `NumProxys | {NID(16) + IP(4 小端)}×N | NumBRs | {PX(2 小端) + IP(4 小端)}×M`。
  → 终端据此建立 `域内代理表 NID→IP` 与 `BR 表 PX→IP`。
  - ⚠ **注意次序**：同步表里每个 Proxy 条目是 **NID 在前、IP 在后**，与注册请求里 `IP 在前、NID 在后`相反。

## 6. 与终端开发直接相关的关键机制

- **SID 生成**：`N_sid = 提供方 NID`，`L_sid = 内容哈希`。文件场景 L_sid=SHA1(文件)；
  **Web 场景 L_sid = SHA1(去 query 后的 URL)**（query 不入 SID，但随请求透传到源站）。
- **回送地址判定**（提供端收到 GET 后）：
  - GET 的 `PID_List` 为空 → **域内**，回送 IP = `域内代理表[请求者 NID]`；
  - `PID_List` 非空 → **跨域**，取 `PX = PID_List[-1] >> 16`，回送 IP = `BR 表[PX]`。
- **跨域 DATA 的 PID 处理**：提供端发 DATA 时 `R=1`，`PID_List = GET 的 PID 序列`，并在末尾**追加一个保留 PID(0)**；
  `PID_Pointer = 有效 PID 数`。BR 据此把数据沿反向路径送回。
- **注册/同步**：终端启动先向 RM 发注册（CONTROL 5），收到同步（CONTROL 6）后才开启业务功能。
- **校验和**：16 位反码和（大端按字累加、折叠进位、取反）；接收侧对覆盖区再算得 0 即合法。

## 7. Web 化改造：把"先拉后推"用于双向 HTTP

GET 不带 payload，消费端无法直接把 HTTP 请求推给提供端；且 GET 沿途累积的 PID **消费端自己看不到**
（是它发出之后才被加上的），只有提供端能看到完整 PID 序列。改造方案（对应《示意图.png》）：

```
消费端C                                                  提供端P
  │  ① GET(SID, 无 payload) ──────────────────────────▶│ 校验 SID → 记未决事务
  │ ◀── ② 隧道 DATA(B=0, 空载, 携带 PID 序列) ───────────│ 让 C 取得合法跨域 PID 隧道
  │  ③ ACK(B=1, payload = 完整 HTTP 请求) ──────────────▶│ 取出请求 → 回源真实 Web 服务器
  │ ◀── ④ 响应 DATA(B=0, payload = HTTP 响应) × N ───────│ 把响应发回
```

- **②** 让请求端拿到合法 PID 序列（隧道）；**③** 复用 **ACK(B=1) 通道并扩展其 payload** 承载 HTTP 请求。
- **load[0] 约定（本项目扩展，沿用原 DataFlag 低位）**：高 2 位标识用途——
  `0x10` TUNNEL（隧道，空载）/ `0x20` HTTP_REQUEST / `0x30` HTTP_RESPONSE；低位 `0x01` = 最后分片 LAST。

## 8. v1 暂不使用的 CoLoR 特性（了解即可）

为聚焦最小功能，新终端 v1 **不使用**以下 CoLoR/参考实现特性：
- **ESS 端到端加密**（AES/ECDH）；（注：**HMAC（C 标志）已实现**——提供端对发出的 DATA 生成/填充以通过 BR 校验，见 `docs/软件说明书.md` §4；此处仅 ESS 加密与「入站 HMAC 校验」不做）
- **可靠传输**：滑动窗口、ACK 重传（参考实现的 `slideWindow.py`）——v1 走 best-effort；
- **QoS** 字段、**分片（Segment）重组**的完整实现、**摘要 GET**、视频流等。

这些是后续（v2+）可演进的方向，地址空间/报文格式已为其预留字段。
